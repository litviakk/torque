# torque

Swiss army knife Ops CLI and Babashka plugin library for the infrastructure. Single `bb torque` entry point covering the operational lifecycle of our services — from build through diagnose, deploy, and beyond. Modules can also be required directly in `bb.edn` tasks as a library. Designed to be invoked by humans and AI agents alike via skills.

What's in scope and what's not is enumerated in [Scope](#scope) below — the surface grows over time, and the principle is that everything covered shares one CLI, one help system, one engine abstraction.

## Vision

Ops work today is scattered across `bb`, ansible, terraform, manual SSH. Torque unifies it under one tool with a consistent interface and data-driven configuration. Each module is independently useful; together they give enough leverage to own an operational task end-to-end — whether the operator is a human or an AI agent running a skill.

```bash
# Is mlflow reachable from my machine?
bb torque nool mlflow --local

# Is mlflow healthy on the server?
bb torque nool mlflow

# List all managed tokens and their expiry
bb torque passe cles

# Rotate the mlflow API token
bb torque passe rotate mlflow
```

## Conceptual Model

Torque is a **typed effect system for ops** with multiple frontends rendering the same effect trace:

- **Modules** declare *intents* (effect types): `:nool/check`, `:registry/sync`
- **Engines** *interpret* those intents in a given execution context
- **Core** *dispatches*: resolves the right interpreter for the context, generates a `:run-id`, and assembles the effect trace
- **dial**, `--json`, and **audit** are *observers* of the same trace — humans, machines, and logs see the same events, differently rendered; none of them drive execution
- **`--plan` flag** returns the effect description as pure data without invoking any interpreter — effects exist as descriptions before they are executed. Handled at the core dispatch level, not inside engines.

## Infrastructure Context

**The Stack:**
- **IaC**: Terraform defines infrastructure as code (Hetzner Cloud, Incus, k3s, DNS, networking)
- **Services**: Run in Incus LXC containers or k3s (Kubernetes); dnsmasq resolves hostnames and subdomains
- **Image Building**: Buildkit builds OCI images; core services use buildkit by default with few exceptions
- **Development Access**: WireGuard VPN tunnel connects developers to internal network; DNS resolver routes to dnsmasq on VPS
- **Task Automation**: Babashka (`bb`) runs common tasks; torque unifies operational tasks under one CLI

**Torque's Role:**
Torque is the **operational SDK** — modules read from a registry (generated by Terraform via `bb torque registry sync`) and coordinate work across the SDLC stages torque covers (see [Scope](#scope)). The registry is the single source of truth: Terraform defines it, torque reads from it, modules use it.

**Why this matters:**
- **nool diagnostics**: Proves infrastructure is correctly configured (locally via WireGuard; remotely via SSH to Incus/k3s services)
- **registry sync**: Keeps application config in sync with infrastructure (no hardcoded service names/IPs)
- **build module**: Buildkit-backed image builds, integrated with registry for artifact management
- **pluggable engines**: Same business logic (diagnose, build, deploy, …) works across different execution targets (Incus, k8s, Docker, etc)

## Scope

Torque is opinionated about which SDLC stages it owns. The phrase "ops surface" is intentionally broader than "diagnostics + build + deploy" — the goal is one consistent CLI across the operational lifecycle, not a fixed list of three things.

**Stages torque owns or will own:**

| Stage | Status | Module | Notes |
|---|---|---|---|
| Build (compile, package) | covered (Phase 2) | `build` | Absorbs `bb artifact:*` / `bb image:*` tasks. **Requires multi-env registry design** — do not implement until label-partitioned registry is specced (Phase 2 prereq). |
| Artifact / image management | covered (Phase 2) | `build artifact`, `build image` | OCI artifacts to registry; container images. |
| Service registry / config-as-data | covered (Phase 0) | `registry` | Single source of truth. Phase 0: manual EDN + Ansible inventory sync. Phase 1: TF-backed. |
| **Torque config** | covered (Phase 0) | `config` | Owns `torque.edn` — init, get, set, list. `bb torque init` alias onboards from scratch. |
| Diagnose (health, connectivity) | covered (Phase 1) | `nool` | Server-side via SSH; client-side via `--local`. |
| Deploy / release | covered (Phase 3) | `deploy` | Orchestrates plan → confirm → execute. **Requires multi-env registry design** — do not implement until label-partitioned registry is specced (Phase 2 prereq). |
| **Test** | planned — not yet specced | `test` | Run module / service / contract tests through torque so engines (local, CI, mock-shell) are uniform. |
| **Lint / typecheck / format** | planned — not yet specced | `check` (working name) | Quality gates exposed through the same CLI; engines wrap clj-kondo, mypy, pyrefly, eslint, etc. |
| **Secrets / config** | specced | `passe` | API token lifecycle (create, rotate, revoke) across OpenBao KV, Keycloak, and service APIs. See [passe.md](passe.md). |
| **Migrate (schema / data)** | planned — not yet specced | `migrate` | Database migrations, data migrations, with dry-run + rollback. |
| **Rollback / recover** | planned — not yet specced | `rollback` (or `deploy --rollback`) | Deploy without rollback is incomplete; this is a Phase 3+ companion to `deploy`. |
| **Observe (logs / metrics / alerts)** | planned — not yet specced | `logs` / `metrics` | Read-only surface over the existing observability stack; not a re-implementation. |
| **Decommission / teardown** | planned — not yet specced | `destroy` (or `deploy --destroy`) | The counterpart to `deploy`. Discovery: every service that can be deployed should be removable through the same CLI. |
| **IaC provisioning** | planned — not yet specced | `tf` | Wrap Terraform/Terragrunt operations (fmt, plan, apply) under torque. Absorbs `apps/terraform/bb/tf.clj`. Engines per backend (terragrunt, terraform). |
| **Backups** | far future — not yet specced | `backup` | Surface backup operations through torque. Far roadmap; existing infra-level tooling stays as-is until then. |
| **Multi-user support** | far future (Phase 3–4) — not yet specced | (cross-cutting) | Shared registry and config state for teams. Likely requires a database-backed registry backend, access control, and per-user audit trails. Remote registry backends (S3/git, Phase 2) are the stepping stone. Do not design for this until Phase 2 remote backends are live. |
| **Audit / traceability** | Phase 0: core writes JSON to stderr; Phase 2+: `logs` module | `logs` | Phase 0 — core emits structured audit records (`:run-id`, `:timestamp`, `:user`, `:module`, `:status`, `:exit-code`, `:duration-ms`) to stderr JSON. Phase 2+ — `logs` module ships with pluggable write backends and `bb torque logs list / show <run-id>` CLI surface. |
| **Docs / discovery** | covered for free by self-registration (Phase 0) | (core concern) | Self-registering modules expose `summary`, `doc`, `examples` — `bb torque docs <module>` and `bb torque` (no args) are derived from this. No separate `docs` module needed. |
| **Guided workflow TUI** | planned (Phase 2) | `dial` (extension) | Rich terminal UI components — list pickers, selection menus, multi-field forms. Replaces line-by-line prompts for destructive or multi-step operations (`passe rotate`, `deploy`, `migrate`). Phase 0 `dial` ships with spinner + line prompts; Phase 2 upgrades to full TUI components. |
| **Health check / remediation** | free from `:ready?` + `:fix` (Phase 1) | `medicin` (alias: `medicine`) | Runs all registered engine `:ready?` probes, collects failures with their `:fix`, presents remediation steps. Agents can auto-dispatch fixes based on `:category`. No extra spec work — falls out of the engine contract. |

**Stages explicitly out of scope:**

- **Writing / editing code** — IDE/editor concern.
- **Code review** — handled by GitHub and humans.

**Principle for adding new modules:** if a stage is in the "planned" list above, it's a candidate. Adding a new module costs ~zero coordination once self-registration is built (see [Design Principles](#design-principles) and [core.md](core.md#module-self-registration)) — drop a namespace, require it from `torque.core`, done. So the right move is to commit to the **framework** now and grow the surface incrementally; not to design every module up front.

## Registry

`src/clj/torque/registry.edn` — shared data across all modules. Committed to git; IaC is the source of truth, registry is the generated snapshot.

Adding a service: add to Terraform → `bb inventory:generate` → `bb torque registry sync`. Do not commit `registry.edn` to git — it may contain private hostnames, IPs, and env vars. See [registry.md](registry.md) for the `.gitignore` recommendation.

The `registry` module owns this lifecycle. All other modules read from it.

## Architecture

```
src/clj/torque/
  registry.edn        — shared service data
  core.clj            — bb entry point, top-level dispatch, engine selection, workflow control
  dial.clj            — UX layer: spinner, result rendering, error formatting (pure UX)
  config/
    core.clj          — config module: init, get, set, list for torque.edn (Phase 0)
  registry/
    core.clj          — registry interface (load, service, services, validate!)
    tf_engine.clj     — Terraform-backed sync (Phase 1+)
  nool/
    core.clj          — check coordination (delegates execution to selected engine)
    local.clj         — local nool engine: L4 TCP, L5/L6 TLS, L7 HTTP (Phase 1)
    ssh.clj           — SSH nool engine: systemd, socket, localhost (Phase 1)
  build/
    artifact.clj      — OCI artifact build + push (Phase 2)
    image.clj         — container image build (Phase 2)
  deploy/
    service.clj       — deployment orchestration (Phase 3)
```

**Engine abstraction**: Operations have pluggable engines. Core defines WHAT; engines define HOW. Example: nool checks work via local nool engine (L4–L7 client-side) or SSH nool engine (server-side health); registry sync works via TF registry engine.

`bb.edn`: `src/clj/torque` on `:paths`. Use via `bb torque <module> <subcommand>` or require namespaces directly (e.g. `[torque.nool.local :as nool]`).

## Backend Engines

Operations (build, deploy, etc.) are abstracted from *how* they happen. Each operation declares a high-level intent; a pluggable **backend engine** implements it.

Example: `build artifact` operation
- **Intent**: "Build and push artifact `foo` to registry"
- **Engines**: 
  - `docker` — use Docker CLI + `docker push`
  - `buildkit` — use Buildkit daemon (remote builds, caching)
  - `nix` — use Nix flakes + `nix build` (hermetic, reproducible)

Engines are swappable per environment or global config. All engines satisfy the same contract:
- Accept a `plan` (data-driven spec: what to build, from where, push where)
- Return execution results in a common shape
- Throw `ex-info` with a fix hint on failure

Module code (nool, build, deploy) never knows which engine is running — it calls a generic interface. Core (or module code) dispatches to the right engine. Engines handle execution policy (confirm, timeout, retry, non-interactive) and return results to dial for display.

**Benefit**: Same business logic (what to check/build), multiple execution strategies (how) without code duplication.

## Configuration

Torque reads an optional `torque.edn` config file at startup. Owned and managed by the `config` module. Discovery order:

1. Path in `TORQUE_CONFIG` env var (if set)
2. `./torque.edn` in the current working directory

```edn
{:registry {:backend :local          ; :local | :s3 | :git (future)
            :path    "registry.edn"} ; path relative to config file location
 :labels   {:env :dev}               ; global label context — applied to all registry lookups
 :passe    {:services [:mlflow]}}    ; services managed by passe (used by passe list)
```

`torque.edn` is optional — torque works without it, applying defaults for all missing keys. CLI label args (`:key value`) always override config defaults. See [config.md](config.md).

## Design Principles

- **Multi-user by design** — torque serves three distinct user bases:
  - **Humans**: interactive spinners, formatted output, helpful errors
  - **AI agents**: structured results, no prompts, skills-friendly interface
  - **CI workers**: non-interactive, reproducible, machine-parseable output
  
  Engines adapt behavior per context (`--non-interactive`, `--json`, etc.); dial renders results consistently.

- **Self-documenting, self-registering modules** — there are **no hand-written `bb.edn` wrappers per module**. A module declares its CLI surface (subcommands, args, flags, help text, examples) and an entry-point function; on import, the module calls `core/register` (or core invokes the module's `register` fn). Registration wires:
  - CLI dispatch (`bb torque <module> ...` reaches the right function)
  - `--help` output for the module and its subcommands (generated from the declaration, never duplicated)
  - Discovery: `bb torque` with no args lists all registered modules with their one-line summaries
  - Docs lookup: `bb torque docs <module>` returns the module's structured description (used by skills and agents)
  
  Adding a new module = drop a namespace in `src/clj/torque/<module>/core.clj`, require it from `torque.core`, done. No `bb.edn` edit, no help-text-in-two-places, no separate registration of docs. The contract lives in `core.md`.

- **Data-driven** — registry drives behavior; adding a service = EDN entry, no code
- **Layered** — `dial` = pure UX (spinner, render, format); engines = logic + execution policy; modules = business contracts
- **Engine abstraction** — operations decoupled from implementation; engines are swappable per environment and user context
- **Engines own execution policy** — confirmations, timeouts, retries, dry-runs, non-interactive mode are engine concerns
- **Prereq checks first** — every operation checks required tools before running; throws `ex-info` with install hint if missing
- **Plan before execute** — every operation supports `--plan`, returning pure data before executing anything; handled by core, not engines
- **Composable** — modules are independent, usable as a library or via CLI
- **No versioning in Phase 0–1** — torque has no semver. Versioning is a Phase 3 concern. Do not cache `bb torque docs` output across torque upgrades — the schema may change between phases.
- **Concurrency is the caller's problem** — `registry.edn` has no in-process locking; Concurrent `registry sync` runs are unsafe and must not be run in parallel — document this at the sync call site. For KV writes, OpenBao CAS (check-and-set) is the concurrency primitive; the `bao` engine must use CAS on all writes.
- **Compensable pipelines** — multi-step workflows (passe rotate, future deploy and migrate) are structured as a sequence of steps with paired compensate functions. Rotate's revoke is the compensate for create; this pattern is implicit in Phase 0 and will be surfaced as a first-class core primitive in Phase 2+ for deploy and migrate.

## Delivery Phases

Torque is delivered in phases. The detailed roadmap is deferred until the contracts in this spec stabilise; this is the high-level sequence:

- **Phase 0 (POC)** — `core` + `config` + `dial` + `registry` (manual EDN + Ansible inventory sync) + `passe`. `bb torque init` onboards from scratch. Proves multi-engine orchestration end-to-end. Real immediate value — token rotation automated. Ansible inventory already exists; TF sync deferred to Phase 1.
- **Phase 1 (Alpha)** — `nool` local + SSH engines, L3 checks (macOS), `registry sync` TF-backed, multi-service registry, label selectors, `medicin`.
- **Phase 2 (Beta)** — `tf` module, `build` module, `logs` module, remote registry backends.
- **Phase 3 (GA)** — `deploy` module, agent skills fully wired, `migrate` module.

**Label selectors** (`:key value` args, e.g. `:env dev :project shadowing`) are the mechanism for scoping operations to any categorical dimension — environment, project, region, or anything else. Registry entries carry label partitions; the registry module filters by the active selector from ctx. No hardcoded env logic anywhere in the stack. Labels are optional — omit to use default partition resolution (see [registry.md](registry.md)).
